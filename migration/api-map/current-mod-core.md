## 0. Corrections to the inventory doc's IP citations (verified against IP source)

The inventory's dispositions all held up, but four of its IP class/member names were originally wrong; they are corrected below (and the inventory doc has since been amended in place to carry these same corrected names):

1. **`McHelper.getServerPortalsNearby` does not exist.** The portal entity-query surface is `IPMcHelper.getNearbyPortals(Entity|Level, …)` (IP imm_ptl/core/IPMcHelper.java:77, :82), built on `McHelper.getEntitiesNearby` (IP imm_ptl/core/McHelper.java:204, :219), plus `ChunkVisibility.getNearbyPortals` (IP imm_ptl/core/chunk_loading/ChunkVisibility.java:68) and `PortalUtils.raytracePortals` (IP imm_ptl/core/portal/PortalUtils.java:31).
2. **`NetherPortalGeneration.onFireLitOnObsidian` does not exist.** The ignition hook lives in the **peripheral** module: `MixinAbstractFireBlock_CVB` redirects `PortalShape.findEmptyPortalShape` inside `BaseFireBlock.onPlace` (IP imm_ptl/peripheral/mixin/common/nether_portal/MixinAbstractFireBlock_CVB.java:20-45) → `IntrinsicPortalGeneration.onFireLitOnObsidian` (IP imm_ptl/peripheral/portal_generation/IntrinsicPortalGeneration.java:71) → `CustomPortalGeneration` forms (`intrinsicToNether` etc., IntrinsicPortalGeneration.java:28-46) → `NetherPortalGeneration.startGeneratingPortal` (IP imm_ptl/core/portal/nether_portal/NetherPortalGeneration.java:110). **Consequence: the port must include `imm_ptl.peripheral.portal_generation`, not just core.**
3. **`ImmPtlNetworking.TeleportRequest` is actually `ImmPtlNetworking.TeleportPacket`** `(int dimensionId, Vec3 eyePosBeforeTeleportation, UUID portalId)` (IP imm_ptl/core/network/ImmPtlNetworking.java:45-47), handled by `ServerTeleportationManager.onPlayerTeleportedInClient` (ImmPtlNetworking.java:76-84).
4. **`TeleportationUtil.checkTeleportation` is actually two methods**: `checkStaticTeleportation` (IP imm_ptl/core/teleportation/TeleportationUtil.java:97) and `checkDynamicTeleportation` (:146), both returning the `Teleportation` record (:61).

On `PortalLinkPayload`: **REPLACE — and the inventory's §2.3 row says the same** (with the full `PortalSyncPacket` citation); the two docs agree and no disposition upgrade exists here (an earlier revision of this note mischaracterized the inventory as saying DELETE). IP portals do NOT sync purely by vanilla entity tracking; they have a dedicated spawn/sync payload `ImmPtlNetworking.PortalSyncPacket(id, uuid, entityType, dimensionId, x, y, z, extraData)` (IP ImmPtlNetworking.java:130-143, doc comment: "server to client, {@link ClientboundAddEntityPacket}, this packet is redirected").

1. **`PortalWorldManager` → `ClientWorldLoader` fusion (hardest gap).** IP-1.21.3 keeps ALL client worlds in maps and swaps `mc.level`/`worldRenderer` via ducks (IP ClientWorldLoader.java:67-69, IEMinecraftClient.java:13); it has NO concept of 26.2's `LevelExtractor`/`SectionUpdateTracker`/`RenderBuffers.endFrame` split.
