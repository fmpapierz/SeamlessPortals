## REFUTED (with corrections)

### R1 — inventory §3.1 step 4: combo-rejection "force-teleported back to the *pre-combo position*" — WRONG position; also miscounts the loop
- **Doc claim:** "up to `teleportLimitPerFrame = 3` successive `tryTeleport` calls; on hitting the limit ... player is force-teleported back to the **pre-combo position** nudged -0.001 along the last portal's surface normal."
- **Reality:** the loop is `for (int i = 0; i <= teleportLimitPerFrame; i++)` (ClientTeleportationManager.java:162) — up to **4** `tryTeleport` calls; rejection fires when the **4th** succeeds (`i == teleportLimitPerFrame`, :171). By then `lastPlayerEyePos` has already been overwritten inside that 4th `tryTeleport` with the **final teleport's checkpoint** (`lastPlayerEyePos = teleportation.teleportationCheckpoint().add(newDelta.scale(adjustment))`, :306-307). The rejection then computes `oldPos = lastPlayerEyePos.subtract(eyeOffset)` (:175-176) and force-teleports to `originalDim` (the pre-combo **dimension**, :159, :178) at that **last-checkpoint-derived position** nudged `worldSurfaceNormal * -0.001` (:179), velocity `normal * -0.1` (:181-183). Only the dimension is "pre-combo"; the position is not.
- **Severity:** minor (the nudge sign, velocity, and reject-the-combo intent are all correct; anyone re-implementing from the doc's prose instead of the code would get the restore position wrong).

### R2 — inventory §3.6: "after **10 consecutive** wrong-dimension packets the server gives up" — off by one
- **Reality:** `ip_wrongMovePacketCount += 1; if (ip_wrongMovePacketCount > 10) { forceTeleportPlayer... }` (mixin/common/position_sync/MixinServerGamePacketListenerImpl.java:155-165) — the force-teleport fires on the **11th** consecutive wrong-dimension packet. ("Consecutive" is correct: the counter resets to 0 on a matching-dimension packet, :171.)
- **Severity:** trivial-minor.

### R3 — inventory §2.4 / §4: "`SimpleSoundInstance` **9-arg** constructor" — it is the 8-arg constructor
- **Reality:** `new SimpleSoundInstance(soundEvent, soundSource, volumeAtPortal, soundPitch, RandomSource.create(seed), x, y, z)` = **8** parameters (CrossPortalSound.java:76-85). The 26.2 ctor at the api-map's citation matches this 8-param shape exactly (SimpleSoundInstance.java:92) — the api-map row is correct; only the inventory's arity label is wrong. (The 9-arg count belongs to `ClientLevel.playSound(x,y,z,event,source,vol,pitch,distanceDelay,seed)`, which the inventory states correctly.)
- **Severity:** trivial-minor.

### R4 — api-map CHANGED row "ServerPlayer.stopRiding bypass": "the stop bypass becomes `super.removeVehicle()` (**skipping only the effect-removal packets**)" — incomplete packet list
- **Reality:** `ServerPlayer.removeVehicle()` (ServerPlayer.java:2138-2150) sends the `ClientboundRemoveMobEffectPacket`s (:2141-2145) **and** a `ClientboundSetPassengersPacket(oldVehicle)` (:2147-2149). A `super.removeVehicle()` bypass therefore also skips the passenger-list sync packet — a real behavioral difference the porter must audit (the row's own "sends ClientboundRemoveMobEffectPacket s" description of :2138-2149 has the same omission). The row's general instruction ("Re-audit what packets each override sends") mitigates, but the parenthetical is wrong as stated.
- **Severity:** minor.
