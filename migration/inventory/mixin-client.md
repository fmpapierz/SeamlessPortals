## 1. Overview

This slice is IP's entire client-side integration surface with vanilla Minecraft: ~62 mixins that (a) make the client hold and tick **multiple `ClientLevel`s at once** (ClientWorldLoader's world-switching model), (b) drive IP's **per-frame portal render pipeline** off `GameRenderer`/`LevelRenderer`, (c) route **cross-dimension interaction, sound, particles and packets** through the correct world, and (d) expose private vanilla state via **duck interfaces** (`qouteall.imm_ptl.core.ducks.*`) so IP core code can swap fields like `Minecraft.levelRenderer`, `ClientLevel.chunkSource`, or `Camera.position` at runtime. Almost every mixin here is a thin trampoline: the real logic lives in IP core classes (`ClientWorldLoader`, `PortalRenderer`/`RenderStates`/`WorldRenderInfo`, `CrossPortalEntityRenderer`, `FrontClipping`, `ClientTeleportationManager`, `BlockManipulationClient`, `PacketRedirectionClient`), and the mixin only decides *when* to call it and *which* vanilla private state to hand over.

Architecturally the slice splits into two halves with very different migration risk. The **sync/interaction/sound/multiworld half** touches stable APIs (packets, `ClientPacketListener` handlers, `MultiPlayerGameMode`, `ClientLevel.playSound`) and should port near-1:1. The **render half** is the 26.2 rewrite hotspot: it injects into `LevelRenderer`'s framegraph lambdas (`method_62214` = addMainPass body, `method_62216` = weather pass, `method_62218` = clear lambda), overrides terrain-visibility discovery (`setupRender`), mutates `RenderSystem`/`GlStateManager` global GL state (fog, cull, shader clipping uniform), patches depth-stencil formats into `RenderTarget`/`MainTarget`, and rewrites GLSL at `CompiledShader.compile` time. Every one of those anchors is expected to have moved or vanished in 26.2's SubmitNodeCollector/RenderPass pipeline.

## 3. Mechanisms

### 3.1 Client tick → render frame sequencing (teleportation is checked twice per frame)
The canonical ordering is documented in a javadoc at `MixinMinecraft.java:86-103`: tick entities (last-tick pos ← current pos; portal animation states rotate) → end tick → **partialTick 0** → update portal animation → manage teleportation → render (interpolating last↔current). Concretely:
- **Tick side** (`MixinMinecraft.java:119-142`, injected after `ClientLevel.tick`): `ClientWorldLoader.tick()` ticks all remote client worlds, then `RenderStates.setPartialTick(0)` → `StableClientTimer` → `ClientPortalAnimationManagement.tick()` (must be after remote-world ticking) → `ClientTeleportationManager.manageTeleportation(true)`.
- **Render side** (`MixinGameRenderer.java:70-100`, `render` HEAD): `RenderStates.updatePreRenderInfo(partialTick)` → `StableClientTimer.update` → `ClientPortalAnimationManagement.update()` (comment: must update before teleportation) → `ClientTeleportationManager.manageTeleportation(false)`. So teleport decisions are made both at tick boundaries (partialTick forced to 0) and per-frame (real partialTick) — a core IP-fidelity invariant.
- Entity-side pre-tick: `MixinClientLevel.java:153-160` calls `ip_tickCollidingPortal()` per entity at `tickNonPassenger` HEAD, i.e., "right before setting last tick pos to this tick pos".

### 3.2 Portal render pass bracketing (GameRenderer ↔ LevelRenderer)
The portal renderer (`IPCGlobal.renderer`, a `PortalRenderer` selected per frame by `PortalRenderer.switchToCorrectRenderer()` at `MixinGameRenderer.java:113`) is driven by brackets:
1. `prepareRendering()` before `GameRenderer.renderLevel` (`MixinGameRenderer.java:103-116`), `finishRendering()` + `RenderStates.onTotalRenderEnd()` + `GuiPortalRendering._onGameRenderEnd()` + optional `lateUpdateLight()` after (:119-142).
2. Inside `GameRenderer.renderLevel`, the actual `LevelRenderer.renderLevel(...)` call is wrapped (`MixinGameRenderer.java:169-184`) so `onBeforeHandRendering(modelView)` runs right after the world (and all recursive portal views) are drawn — this is where the recursion unwinds before the hand is drawn; `onHandRenderingEnded()` fires at `renderLevel` TAIL (:162-167).
3. Within `LevelRenderer`'s main framegraph pass (`method_62214`), sub-brackets fire at fixed vanilla landmarks: entity-rendering begin at `constantAmbientLight` check, entity-rendering end after the second `endLastBatch`, translucent begin at `Sheets.translucentItemSheet`, per-layer clipping around each `renderSectionLayer` call (`MixinLevelRenderer.java:123-232`). Weather and sky passes get their own bracketing via the `addWeatherPass` lambda and a wrapped `FramePass.executes` runnable in `addSkyPass` (:364-442).
4. The camera view matrix itself is transformed by wrapping the `Matrix4f.rotation(quat)` call in `GameRenderer.renderLevel` through `TransformationManager.processTransformation` (`MixinGameRenderer.java:304-317`), and the *pre-bobbing* projection is captured/substituted via the `getProjectionMatrix` redirect (:277-302) so portal frusta are built from an un-bobbed projection.

### 3.3 Portal-view terrain discovery replaces vanilla BFS
When rendering a portal view, vanilla `LevelRenderer.setupRender` is cancelled at HEAD and replaced by `VisibleSectionDiscovery.discoverVisibleSections(...)` operating on IP's own `ImmPtlViewArea` (a hacked `ViewArea` built in `allChanged` via a constructor redirect, `MixinLevelRenderer.java:322-345`), using a *copied* frustum offset by `offsetToFullyIncludeCameraCube(8)` (:234-263). The same discovery can be forced for the main view for N frames via `MyGameRenderer.vanillaTerrainSetupOverride` (:270-306). Because `ViewArea.repositionCamera` never runs for portal cameras, `isSectionCompiled` is rerouted to `ImmPtlViewArea.rawGet` (:491-518). Sections carry a reuse generation mark via duck `IERenderSection.portal_mark` (`MixinRenderSection.java:13-36`). Supporting casts: `Frustum` gets a `FrustumCuller` + original-camera-pos snapshot (portal-plane culling that must ignore the camera-cube offset mutation, `MixinFrustum.java:29-95`), and the frustum offset loop is deadloop-proofed by an `@Overwrite` (`MixinFrustum_FixDeadLoop.java:39-70`).

### 3.4 Front clipping (the portal near-plane)
GLSL for all vanilla shaders is rewritten at compile time (`MixinCompiledShader.java:25-36` → `ShaderCodeTransformation`), each compiled program caches the `iportal_ClippingEquation` uniform location (`MixinShaderInstance.java:28-39`), and the uniform is (re)uploaded at every shader switch (`MixinRenderSystem_Clipping.java:20-56`) and per terrain layer (`MixinLevelRenderer_Optional.java:72-84`). The plane itself is set/cleared around terrain layers and weather (`MixinLevelRenderer.java:185-232, 364-391`). This whole chain assumes 1.21.3's global-current-shader model (`RenderSystem.setShader`) and is a top rewrite risk for 26.2.

### 3.5 Stencil-capable framebuffers
`RenderTarget`/`MainTarget` texture allocation is arg-patched to `GL_DEPTH24_STENCIL8` (or `GL_DEPTH32F_STENCIL8`) + `GL_DEPTH_STENCIL_ATTACHMENT` when the duck flag is on; flipping the flag triggers `resize()` to recreate attachments (`MixinRenderTarget.java:50-160`, `MixinMainTarget.java:27-96`). `IPMixinPlugin.shouldApplyMixin` disables both when `porting_lib` is present (`IPMixinPlugin.java:23-30`).

### 3.6 Mirror rendering face-cull inversion
Odd-mirror-count views need inverted face culling: applied around terrain layers and the sky pass (`MixinLevelRenderer.java:203-205, 434-441`), and for entity/BE batches by force-holding cull off during `BufferSource.endBatch` (`MixinMultiBufferSourceBufferSource.java:15-35`) with `GlStateManager._enableCull` suppressed while the flag is set (`MixinGlStateManager.java:22-32`).

### 3.7 Multi-world client (one `ClientLevel` per dimension, simultaneously)
`MixinClientLevel` swaps in IP's client chunk manager at construction (:97-110) and exposes mutable `connection`/`chunkSource`/`levelRenderer`/`tickRateManager`; `MixinMinecraft` exposes mutable `levelRenderer`/`mainRenderTarget`/`renderBuffers`; `MixinGameRenderer` exposes mutable `mainCamera`/`lightTexture`; `MixinParticleEngine`/`MixinClientPacketListener`/`MixinAbstractClientPlayer` expose their `level` fields. Together these let `ClientWorldLoader.withSwitchedWorld` re-point the entire client onto another dimension and back. Per-world renderers get isolated `SectionBufferBuilderPool`s (`MixinSectionRenderDispatcher.java:30-46`) with tiny initial buffers (`MixinSectionBufferBuilderPack.java:19-32`); window resize propagates to all secondary renderers (`MixinGameRenderer.java:187-198`); the main renderer's `allChanged` reload fans out via `ClientWorldLoader._onWorldRendererReloaded()` and is suppressed mid-portal-render (`MixinLevelRenderer.java:394-414`).

### 3.8 Dimension-stamped movement packets & server-authoritative correction
Every `ServerboundMovePlayerPacket` is stamped with the player's dimension at construction (`MixinServerBoundMovePlayerPacket.java:15-25`) and the stamp is appended to the wire format by all four subclass `write` mixins — only when `ImmPtlNetworkConfig.doesServerHaveImmPtl()` (vanilla-server compat). Inbound, `ClientboundPlayerPositionPacket` reads an appended dimension (`MixinClientboundPlayerPositionPacket.java:17-23`), and `handleMovePlayer` force-teleports the client player if the packet dimension disagrees with the client (`MixinClientPacketListener.java:88-129`). This is the client half of IP's position-sync protocol (server half in `common.position_sync`).

### 3.9 Packet redirection execution context
Redirected packets (wrapped server→client packets targeting a non-main dimension) must be handled against the right `ClientLevel`: `Minecraft.wrapRunnable` wraps deferred tasks in `withSwitchedWorldFailSoft` when `PacketRedirectionClient.clientTaskRedirection` is set, and an overridden `scheduleExecutables()` prevents vanilla from deferring handling while a redirected message is being processed on-thread (`MixinMinecraft_RedirectedPacket.java:23-59`).

### 3.10 Cross-dimension block-change prediction ack
Vanilla's block-change acknowledgement is per-`BlockStatePredictionHandler` (one per `ClientLevel`); IP keeps all handlers' `currentSequenceNr` synchronized on `startPredicting` (`MixinBlockStatePredictionHandler.java:23-32`) and fans the server ack out to all worlds (`MixinClientPacketListener.java:206-217`). Rationale javadoc: `MixinClientPacketListener.java:195-205`.

### 3.11 Cross-portal interaction (attack/use/pick through a portal)
`GameRenderer.pick` computes the remote pointed block after the vanilla pick (`MixinGameRenderer_B.java:25-30`); `Minecraft.handleKeybinds` actions are run in a switched-world context when pointing through a portal (`MixinMinecraft_B.java:37-130`); `MultiPlayerGameMode`'s outgoing action/use packets are re-wrapped into dimension-tagged RPC packets (`MixinMultiPlayerGameMode.java:115-144`), and its uses of `player.level()` are redirected to the switched `mc.level` (:41-80).

### 3.12 Cross-portal sound
`ClientLevel.playSound` on a far/remote position is rerouted through `CrossPortalSound.createCrossPortalSound` (sound played at the portal-transformed position); remote-world sounds with no transferring portal are muted (`MixinClientLevel_Sound.java:28-65`); the delayed-play fallback is an `@IPVanillaCopy` of vanilla's distance-delay logic (:67-76).
