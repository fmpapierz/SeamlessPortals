## 1. Overview

This slice is IP's **glue layer**. The `ducks/` package is 36 interfaces that expose private vanilla state/behavior: each duck is `implements`-ed onto a vanilla class by a mixin, and the rest of IP casts vanilla objects to the duck to call `ip_*`/`portal_*` methods. Ducks are the *contract surface* between IP's subsystems and vanilla internals — every duck method that a mixin implements with `@Shadow` fields is a direct dependency on a vanilla field/method that must be re-verified for 26.2. `api/` is the small stable public API other mods use (`PortalAPI` static facade + `ImmPtlEntityExtension` opt-out hook + a worked GUI-portal example). `commands/` is the `/portal` command tree — the debugging and content-creation workhorse — plus the client-side `/imm_ptl_client_debug` tree and three custom Brigadier argument types.

`block_manipulation/` implements **cross-portal block interaction** (point at a block through a portal, break/place/pick it): a client half that re-raytraces through the portal into the destination `ClientLevel` and swaps interaction context, and a server half that receives redirected interaction packets via IP's RPC utility and replays vanilla packet-handler logic (marked `@IPVanillaCopy`) against the destination dimension with its own reach validation. `mc_utils/`, `miscellaneous/`, `debug/`, `redstone/` are small support classes: per-server deferred task list, NBT pretty-printer (vanilla copy), debug wireframe renderer, performance/GC monitors, first-run screen, and two empty placeholders.

## 3. Mechanisms

### 3.1 The duck pattern (how IP reaches vanilla internals)

Every private vanilla field/method IP needs is exposed one of two ways: (a) a duck interface in `ducks/` + `implements` on a mixin (callers cast the vanilla object), or (b) a mixin `@Accessor`/`@Invoker` interface living in the mixin packages (e.g. `IEChunkMap_Accessor.ip_getChunks()` used by PortalDebugCommands.java:459). Naming conventions: `ip_` and `portal_` prefixes only; no `@Unique`-name collisions with vanilla. Several ducks impose *behavioral contracts* beyond field access that the port must preserve: `IEEntity.ip_setPositionWithoutTriggeringCallback` must NOT trigger entity-section updates (ducks/IEEntity.java:36-38); `IEEntityTrackingSection.ip_traverse` exists to bypass `AbortableIterationConsumer` (ducks/IEEntityTrackingSection.java:11); `IEChunkMap` is split across two mixins so chunk-sync and entity-sync concerns stay separate.

### 3.2 Cross-portal block interaction — client pipeline

1. **Pointing** (every frame): `GameRenderer.pick(F)V` RETURN → `BlockManipulationClient.updatePointedBlock(partialTick)` (MixinGameRenderer_B.java:25-30; HEAD of the same method is cancelled while a portal-view is rendering, :16-23). It clears `remotePointedDim`/`remoteHitResult`, honors the `canDoCrossPortalInteractionEvent` predicate, raytraces portals from the camera with reach = `player.blockInteractionRange()` filtering `portal.isInteractableBy(player)` (BlockManipulationClient.java:64-72). If the portal hit is nearer than the current vanilla target (`getCurrentTargetDistance()`, which treats `PortalPlaceholderBlock` targets as infinitely far, :91-106) + 0.2 slack: vanilla `client.hitResult` is replaced by a *synthetic MISS* at the portal surface (:77) and the ray's remaining segment `[beginDistance, endDistance]` is transformed with `portal.transformPoint(...)` into destination-space (:117-122).
2. **Destination re-trace**: a `ClipContext(OUTLINE, Fluid.NONE)` drives `BlockGetter.traverseBlocks(from, to, context, perBlock, missFactory)` against `ClientWorldLoader.getWorld(portal.getDestDim())` (:124-174). The per-block lambda is a vanilla-clip re-implementation that additionally **skips `PortalPlaceholderBlock` and `Blocks.BARRIER`** (:140-145) and back-offsets the start by `0.0015 × ray` "to avoid being considered inside block" (:151-153); block vs fluid hit resolved by nearer distance-squared (:160-164). A hit below `world.getMinBuildHeight() + 0.1` is coerced to a DOWN-face hit (:176-183). Only a *non-air* result sets `remotePointedDim` (:185-190).
3. **Interacting**: `Minecraft.handleKeybinds`'s four calls are wrapped (MixinMinecraft_B.java:37-130). When pointing through a portal, `startAttack`/`continueAttack` run inside `withSwitchedContext(supplier, transformHitResult=false)` and `startUseItem` with `transformHitResult=true`; `withSwitchedContext` swaps the world via `ClientWorldLoader.withSwitchedWorld` and swaps `client.hitResult` → `remoteHitResult` for the duration (BlockManipulationClient.java:197-231). `pickBlock` does a manual `Minecraft.level`/`hitResult` field swap instead (MixinMinecraft_B.java:110-126). Because the *player's* level field is NOT switched, `MixinMultiPlayerGameMode` redirects `LocalPlayer.level()` calls inside `startDestroyBlock`'s lambda (`method_41930`) and `continueDestroyBlock` to `Minecraft.getInstance().level`, and swaps the `UseOnContext` constructor in `performUseItemOn` for the variant taking an explicit level (MixinMultiPlayerGameMode.java:40-80).
4. **Packet redirection**: the `ClientPacketListener.send` calls inside `startPrediction`, `startDestroyBlock`, `stopDestroyBlock` are `@ModifyArg`-intercepted (MixinMultiPlayerGameMode.java:82-113). If `ClientWorldLoader.getIsWorldSwitched()`, a `ServerboundPlayerActionPacket` (attacking actions only) or `ServerboundUseItemOnPacket` is serialized with its own `STREAM_CODEC` into raw bytes and wrapped into an RPC packet `McRemoteProcedureCall.createPacketToSendToServer("...BlockManipulationServer.RemoteCallables.processPlayerActionPacket|processUseItemOnPacket", dimension, bytes)` (:115-144). `ServerboundUseItemPacket` (use-item-in-air) is deliberately not redirected (:140).

### 3.3 Cross-portal block interaction — server pipeline

`RemoteCallables.processPlayerActionPacket/processUseItemOnPacket` decode the embedded vanilla packet from bytes (`STREAM_CODEC.decode`), resolve `player.server.getLevel(dimension)` (Validate non-null), then run inside `withRedirect(new Context(world, hitResult), ...)` which (a) sets the `REDIRECT_CONTEXT` ThreadLocal and (b) wraps execution in `PacketRedirection.withForceRedirect(world, runnable)` so every clientbound packet emitted during handling is dimension-tagged (BlockManipulationServer.java:136-202). The handlers are `@IPVanillaCopy` transcriptions of `ServerGamePacketListenerImpl.handlePlayerAction`/`handleUseItemOn` with two changes: the world is the *portal-destination* world rather than `player.level()`, and vanilla's distance check is replaced by `canPlayerReach` (§2.4: same-dim check OR exists nearby interactable portal whose transform lands the player within scaled reach of the target, :70-98). `doProcessPlayerAction` forwards to `player.gameMode.handleBlockBreakAction(pos, action, dir, world.getMaxBuildHeight(), seq)` + `ackBlockChangesUpTo` (:208-225); `doProcessUseItemOn` checks `itemStack.isItemEnabled(world.enabledFeatures())`, `world.mayInteract`, calls `player.gameMode.useItemOn(...)`, swings on `shouldSwing()`, then sends `ClientboundBlockUpdatePacket` for the clicked pos and its offset neighbor (when in build height) via `PacketRedirection.sendRedirectedMessage(player, dimension, packet)` (:237-286).
Placement mapping `getHitResultForPlacing(world, hit)` (used by the *client* before `startUseItem`, :100-134): among **global portals only**, find one whose normal opposes the clicked face (`normal·sideVec < −0.9`), whose projection contains the clicked block (`isBoxInPortalProjection`), and within 0.6 of the plane; if found, transform `hitCenter + 0.501·sideVec` through the portal, and return a new `BlockHitResult` at the transformed block pos with the face **flipped** (`side.getOpposite()`), retargeted to `portal.getDestDim()` — this is what lets you place a block "against" a world-wrapping portal border and have it appear on the other side.

### 3.4 Portal sculpt (`/portal shape sculpt`)

`invokeSculpt` (PortalCommand.java:2670-2789): collect all block collision AABBs touching `portal.getBoundingBox()` via `level().getBlockCollisions(portal, box)` → `VoxelShape.toAabbs()` (:2827-2837), reject > 40,000 boxes. Start from the existing `SpecialFlatPortalShape` mesh copy or a fresh full-quad `Mesh2D` (:2683-2689). On `Util.backgroundExecutor()`: for each box compute its cross-section polygon on the portal plane in portal-local (axisW/axisH, half-extent-normalized) coordinates via `GeometryUtil.getSlicePolygonOfCube` and `mesh2D.subtractPolygon(...)`, compacting every 10,000 boxes, then `simplify()`+`compact()` (:2699-2719). Back on the server thread (`server.execute`): if area ≈ full quad (|4−area|<1e−5) reset to default shape; if area ≈ 0 fail; else `setPortalShapeByMesh` (:2721-2765) — optionally re-fitting portal bounds: normalize mesh points into the mesh bounding box, then move origin/destination by the (portal-local → world via `transformLocalVec`) center offset and scale width/height (:2791-2823). Default animation is suppressed for 5 ticks to avoid a visual pop (:2750-2751); a 5-tick `ServerTaskList` task prints "sculpting in progress" if the future is still running (:2778-2788).

### 3.5 Client performance feedback loop

Once per second (fps-field write in `Minecraft.runTick`): sample FPS + derived free memory → 20-sample window → every 5 s compute `PerformanceLevel` and RPC to `ImmPtlChunkTracking.RemoteCallables.acceptClientPerformanceInfo` (ClientPerformanceMonitor.java:37-96). Server uses this to shrink portal chunk-loading for weak clients. GcMonitor complements it with the `memoryNotEnough` flag (§2.6) polled by chunk-loading code.

### 3.6 Deferred task lists

Server: `ServerTaskList.of(server)` → per-server `MyTaskList` processed at END_SERVER_TICK and force-cleared on server close (ServerTaskList.java:10-18). Tasks are `MyTaskList.MyTask` (return true = done) with combinators `oneShotTask`, `withDelay(ticks, task)`, `withDelayCondition`, `repeat`, `chainTask(s)` — used all over this slice (room creation PortalCommand.java:1908, chunk erase PortalDebugCommands.java:792, sculpt notice :2778). Client analog: `IPGlobal.CLIENT_TASK_LIST` (GcMonitor.java:52).
